            <readWriteMode>read only</readWriteMode>
          </timeSeriesSet>
        </inputVariableDefinition>
        <expression>H + offset</expression>
        <outputVariable>
          <timeSeriesSet>
            <moduleInstanceId>ConvertUnitsCustom</moduleInstanceId>
            <valueType>scalar</valueType>
            <parameterId>H.corrected</parameterId>
            <locationId>Gauge01</locationId>
            <timeSeriesType>simulated historical</timeSeriesType>
            <timeStep unit="hour" multiplier="1"/>
            <readWriteMode>add originals</readWriteMode>

## Field reference

<Aside type="note">
`user`'s `expression` is a plain string (`"X1 + a"`) evaluated at runtime —
the schema can't validate it, so a typo'd variable or coefficient id is a
**runtime** error in the transformation log, not a config-load error.
`custom` is the escape hatch one level further down: a `className` pointing
at a Java class you supply, for logic no built-in function covers.
</Aside>

## Gotchas

- **`user simple`'s `expression` references ids, not element names** — the
  string must use the `variableId`s declared in `inputVariableDefinition`
  and the `id`s declared in `coefficientSet`/`coefficient`, not the FEWS
  parameter or location ids. Mismatched ids fail at run time with no config
  validation to catch it earlier.
- **`lookup simple` still needs a `coefficientSet` even for the simplest
  table** — the [input, output] pairs live inside it, and values between
  defined points are found "using [interpolation type]" per the schema
  annotation (check the specific lookup variant's coefficientSet fields for
  which interpolation applies).
- **`generation` functions don't read any input series for their output
  values** — `constant`, `recessionMean`, `recessionPattern`, and
  `tidalConstituents` synthesize the output from configuration (and, for the
  recession variants, a *history period* read from the same series) rather
  than transforming an input series. Don't expect an `inputVariable` field
  here the way every other category has one.
- **`custom` requires a `className` you (or a plugin) actually provide** —
  unlike every other function's optional `className` override (which falls
  back to a sensible built-in default), `custom`'s class is the *entire*
  implementation. There's no default to fall back to.
